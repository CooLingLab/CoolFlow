# 产品开发中的评审

[English](reviews.md) | **简体中文**

下文的 **Design Review** 和 **Code Review** 是推荐开发方法的一部分。单独的
`flowreviews/scenarios/` 目录包含 CoolFlow 自身的内部 Scenario Review，不是用 CoolFlow 构建
的应用测试。这些案例保留在公开的 CoolFlow 源仓库中；不要复制到目标应用仓库。

## Design Spec Loop 内：编码前评审

当功能新颖、复杂、有风险或不可逆时，考虑独立的 EGM 风格 Goldfish Review。向评审者提供**当前
Spec 草稿**，可选链接的 PRD/设计，以及相关现有代码/背景。独立评审者应：

- 挑战缺失的用户行为、验证案例和失败模式。
- 对照现有代码和约束检查假设。
- 标记过度设计、备选方案和不清晰的取舍。
- 验证实施计划是否详细到足以指导编码 Agent。
- 报告可操作的问题和支持证据。

解决并验证重要阻塞项，然后在编写大量代码前确认设计已准备好实施。小变更可以使用轻量检查。对
**现有代码**进行设计可行性评审，*不是*对新实现的评审。

## Implementation Loop 内：评审已实现代码

- 运行相关测试并检查明显回归。
- 评审**新代码差异**的正确性、安全性、可读性和可维护性。
- 对照 Spec 和验收条件比较代码行为。
- 通过修改代码或与人类明确重新审视需求来解决差异。
- 寻求人类对实际结果的验收；之后同步持久文档。

**人类验收后**，同步持久的功能/领域/Roadmap 文档，并归档相关工作记录。这是一个步骤，不是单独
的 Knowledge Loop。**在任何开发流程步骤**，反馈、新想法或变化的需求只要值得重新考虑产品方向、
假设或范围，就可以激活跨阶段 Evolution Loop，返回任何相关步骤。普通的设计和代码修正仍留在
局部质量 Loop 中；发布后反馈只是 Evolution 的一种可能触发条件。

CoolFlow 不要求 EGM、Spec Kit、OpenSpec 或特定的 Agent runner。这些是可选工具和良好实践来源。
