# 文档规范（v0.1）

[English](documentation.md) | **简体中文**

**设计规则：** 将持久、已验收的项目知识与探索性、进行中的工作分开。**每个事实只保留一个权威
位置**；使用链接，而不是重复段落。

## 标准应用文档树

以下是用 CoolFlow 初始化的应用仓库的**默认文档树**。它描述推荐的项目文档位置与生命周期；
并不要求创建每一个可选文件。

**范围：** 这棵树只描述文档。应用源代码、测试、构建配置、依赖与 CI 属于仓库的源码树，遵循
选定的技术栈和项目约定（例如 `src/` 与 `tests/`，或 `apps/` 与 `packages/`）。不要把生产代码
放在 `docs/` 下。

```text
<app-repository>/
├── AGENTS.md                         # 初始化时必需
├── README.md                         # 初始化时必需
└── docs/
    ├── documentation.md              # 初始化时必需；本地文档规范
    ├── coolflow.yml                  # 初始化时必需；上下文偏好和可选的验收规则
    ├── development-flow.md           # 初始化时必需；按需查阅的参考
    ├── product.md                    # 初始化时必需
    ├── roadmap.md                    # 初始化时必需
    ├── domain.md                     # 初始化时必需
    ├── features/                     # 初始化时必需目录
    │   └── <feature>.md              # 已验收/当前行为；验收后添加
    ├── work/                         # 初始化时必需目录
    │   ├── <objective>/              # 仅在实际工作开始时创建
    │   │   ├── spec.md               # 目标进入 Design Spec Loop 时起草
    │   │   ├── prd.md                # 可选：较大的产品需求
    │   │   ├── design.md             # 可选：更深入的技术设计
    │   │   ├── tasks.md              # 可选：持久任务进度
    │   │   ├── brainstorm.md         # 可选：发现笔记与产品假设
    │   │   ├── validation.md         # 可选：验证证据及其决定
    │   │   ├── competitive-landscape.md # 可选：较完整的竞品/市场研究
    │   │   └── prototypes/           # 可选：原型产物
    │   └── archive/                  # 初始化时必需目录
    │       └── <completed-work>/     # 选择性保留的已完成工作证据
    ├── solutions/                    # 可选：已验证、可复用的工程知识
    │   └── <solution>.md              # 每个文件聚焦一项发现
    ├── architecture.md               # 可选：当前系统架构
    ├── adr/                          # 可选：重要架构决策
    │   └── <number>-<decision>.md     # 每个文件一项决策
    └── feature-map.md                # 可选：实际 UI 导航与验证
```

### 各部分何时创建

| 位置 | 初始化时 | 发现/开发期间 | 验收后 |
|---|---|---|---|
| `AGENTS.md`、`README.md` | 缺失时创建 | 按需维护 | 保持最新 |
| `docs/documentation.md` | 缺失时复制完整本地规范 | 遵循并适配项目需要 | 保持项目约定最新 |
| `docs/coolflow.yml`、`docs/development-flow.md` | 复制默认偏好和离线参考 | 按需更新偏好；只有人类可以编辑 `acceptance` 节 | 保持参考可找到 |
| `docs/product.md`、`roadmap.md`、`domain.md` | 创建带 `status: not_started` 的模板；正文中未知事实保持 `To decide` | 决策成为持久事实时更新，包括进展卡片 | 同步已验收变更 |
| `docs/features/` | 创建目录 | 通常保持不变 | 添加或更新已验收功能描述 |
| `docs/work/` | 创建目录 | 发现阶段有需要时打开目标目录；进入 Design Spec Loop 时创建其 `spec.md` | 选择性归档 |
| `docs/work/archive/` | 创建目录 | 无需填充 | 保留有用的历史证据 |
| `docs/solutions/` | 默认不创建 | 只有在验证了非显而易见、持久且有实质意义的工程发现时创建 | 保持有用发现最新；删除误导或过时内容 |
| `docs/adr/` | 默认不创建 | 当重要的架构或技术决策需要持久理由时，创建一条记录 | 保留历史；用新 ADR 取代旧决策，而不是重写旧记录 |
| 可选文档 | 默认不创建 | 只有复杂性或真实需要证明其价值时才添加 | 相关时维护或归档 |

**初始化时必需** 是指在模板骨架中创建缺失的文件/目录。它不表示要编造内容、创建空的功能文档，
或开始一个实施目标。

**在发现阶段**，目标目录可以只放笔记或原型，不写 Spec。**当选定的目标进入 Design Spec Loop**
时，编写其统一的 `spec.md`，定义可实施的设计与验证标准。仅仅进行头脑风暴并不要求 Spec；可选
产物不是固定检查清单。

### 这棵文档树刻意不规定什么

- CoolFlow v0.1 不要求默认创建 `docs/solutions/`、`docs/adr/`、`docs/knowledge/` 或
  `docs/state.md`。
- `docs/solutions/` 是已验证、可复用工程知识的推荐可选位置。它不在初始化时创建。
- `docs/adr/` 是架构决策记录（ADR）的可选位置：每个文件一项重要决策。它不在初始化时创建。
- CoolFlow 自己的 `flowecosystem/` 目录属于 **CoolFlow 方法论仓库**。它收录外部框架与方法，
  不会被复制到应用仓库。应用的 `docs/solutions/` 是它自己的工程知识库；两者名称相关，但用途
  不同。
- 项目可以在初始化后自定义文档名称和位置。每个事实保留一个权威位置，并保持项目本地
  `AGENTS.md` / README 导航准确。
- 进展元信息放在各文档的头部（见下文“第 1～5 步进展元信息”）；它不需要单独的状态文件、
  引擎或任务清单。

## CoolFlow 上下文偏好

`docs/coolflow.yml` 的 `context_mode` 保存项目级偏好。新项目默认为 `auto`，修改该值即可切换模式。工作进展仍保存在原有记录中。同一文件还可以包含可选的 `acceptance` 节，见[验收分级](#验收分级)。

| 请求 | `auto` | `manual` |
| --- | --- | --- |
| 规划新项目或重新评估产品方向 | 读取 `docs/development-flow.md`，后续只查阅与当前方向相关的项目记录。 | 使用用户提供的上下文。仅在用户明确要求时读取流程参考。 |
| 未指定目标的接续请求 | 从进展卡片、Spec 等项目记录中查找相关的当前工作。存在唯一明确的匹配时接续，否则询问。 | 搜索前先问用户要接续哪项工作，即使项目里只有一个活跃目标。 |
| 已指定目标、Spec 或具体维护任务 | 直接读取与任务相关的项目文件。 | 直接读取与任务相关的项目文件。 |

未指定目标的接续请求须先确定模式，再查找工作记录。文件缺失时按 `manual` 处理。文件存在但无法读取、格式错误或没有有效的 `context_mode` 值（`auto` 或 `manual`）时，按 `manual` 处理，并在读取配置时报告问题。两种模式均遵循项目工作规则，并响应用户明确提出的查阅方法论或报告项目进展的请求。若用户未指定接续目标，同时询问下一步，则按上表的接续规则处理。

## 第 1～5 步进展元信息

第 1～5 步（Idea → Brainstorm 到 UI Prototype）产出的是持续演进的文档，而不是已验收行为，因此
记录这些工作的文档顶部都有一张简短的**进展卡片**。人和 Agent 无需先读正文，就能判断工作进展
到哪里。

适用于 `docs/product.md`、`docs/roadmap.md`、`docs/domain.md`，以及 `docs/work/<objective>/`
下记录第 1～5 步进展的工作文档，例如 `brainstorm.md` 或 `competitive-landscape.md`。不适用于
`AGENTS.md`、`README.md`、`docs/documentation.md`、`docs/features/`、`docs/solutions/`、
`docs/adr/`，也不适用于面向单个目标的 `prd.md`、`spec.md`、`design.md` 和 `tasks.md`——它们
保留自己的文档状态，通过自身内容、代码和验收证据跟踪进展。

```yaml
---
status: in_progress
related_steps: [1]
progress_updated: "2026-11-16"
current_progress: "已初步梳理目标用户，正在讨论使用场景。"
next_steps:
  - "了解用户最常遇到的问题。"
open_questions:
  - "是否同时面向团队用户？"
---
```

| 字段 | 必需 | 取值 |
|---|---|---|
| `status` | 是 | `not_started`、`in_progress`、`paused` 或 `complete`。 |
| `related_steps` | 是 | 文档相关的流程步骤 1～5，例如 `[1]` 或 `[1, 4]`。 |
| `progress_updated` | 否 | 上次更新进展的日期，写成带引号的 `"YYYY-MM-DD"`。 |
| `current_progress` | 否 | 一到两句：已经完成什么、正在进行什么。 |
| `next_steps` | 否 | 接下来打算做的简短列表。 |
| `open_questions` | 否 | 尚未解决的问题或决定。 |

规则：

- 该块必须是文件的第一段内容，位于一级标题之前，并保持简短——它是一张卡片，而不是第二份
  文档。可能被 YAML 误解析的值要加引号（`progress_updated` 日期必须加引号），`status` 这类
  短枚举值不必加引号；多项文字使用块列表；块内不写注释。
- `status` 描述**本文档所记录的工作**，既不表示整个项目，也不表示唯一的当前阶段。多份文档可以
  关联同一步骤，一份文档也可以关联多个步骤而只有一个状态；`related_steps` 表示相关，不表示所列
  每个步骤都处于该状态。
- 文档缺失或没有该块**不能**作为 `not_started` 的证据。没有进展元信息时，应记为“未找到记录”，
  直到有人确认。
- 卡片是人工确认工作的**快照**，不能证明需求已验收、代码已存在或验证已完成。`complete` 表示
  所记录的工作达到预期终点；验收和发布是另外的事。
- 状态的权威位置只有一个。使用该块的文档不再同时保留 `> Status:` 行。
- 可选字段只在有实际工作时填写。核心文档的新模板使用 `status: not_started` 和 `related_steps`；
  新建的工作文档使用 `status: in_progress`，因为创建它就意味着工作已经开始。在产生真实进展
  之前，不要向其余字段填入占位文字。
- 工作文档由真实内容构成：只包含工作实际覆盖的章节，其余章节直接省略，不要照搬未填写的模板
  标题，也不要在其下留 `To decide`。只有在明确需要一份空起始结构时，才复制完整模板。
- 文档进展发生实质变化时更新卡片。读者把 `progress_updated` 视为新鲜度的提示，而不是正文仍然
  准确的证明。
- 查看第 1～5 步进展时，先读卡片，需要时再打开正文。请求第 1～5 步概览时，列出全部五个步骤，并区分
  `not_started` 与“未找到记录”；不能仅凭相关文档推断某一步骤的状态。通用项目概览不受这些卡片的
  范围限制：可以使用相关 Spec、代码和验收证据覆盖适用的生命周期，不必强制输出完整的八步报告。
- 核心文档的默认映射为 `product.md` → `[1]`、`domain.md` → `[2]`、`roadmap.md` → `[4]`。如果
  项目的实际组织方式不同，可以调整映射，并把该选择记录到项目本地规范中。

## 交付进展（第 6～8 步）

在现有统一 Spec 的 `Delivery progress` 节中记录特定工作目标的交付进展。如果项目本地约定把这类信息放在已有的验收或交付记录中，沿用该权威记录。每个事实只在一个权威位置查阅和更新，其他处维护的证据用链接引用。Spec 的文档状态与交付进展分别记录。第 1～5 步进展卡片维持原有范围。

| 字段 | 取值 | 依据 |
| --- | --- | --- |
| Implementation（实现） | `not_started`、`in_progress`、`implemented` | 实际观察到的变更及其范围或版本。使用 `implemented` 需要有证据表明约定的行为已实现。 |
| Verification（验证） | `not_verified`、`partially_verified`、`verified` | 对应版本或范围的实际检查、结果和缺口。所需验证仅完成一部分时用 `partially_verified`。 |
| Acceptance（验收） | `pending`、`accepted`、`accepted_by_policy`、`changes_requested` | 记录适用范围的明确人工决定；按项目[验收分级](#验收分级)完成的 `low` 改动记录 `accepted_by_policy`。已确定正在等待决定时用 `pending`。 |
| Release（发布） | `not_released`、`released` | 分别记录明确发布授权和实际结果。有证据说明发布了什么、发布到哪里时用 `released`，并记录已有的发布后检查。 |

仅记录有依据的字段，并说明重要未知项。只有证据能确定指定范围的对应状态时，才使用 `not_started`、`not_verified` 或 `not_released`。授权、验收和发布是独立的事实。发生实质变更后，保留此前验证、验收和发布证据的适用版本，记录当前缺口，并在需要时获取新证据或人工决定。

在授权工作中，有了实质的实现与验证结果就记录，并在人工明确作出决定时记下决定。验收后，按文档同步规则更新受影响的长期文档。执行发布需要单独授权。若目标的权威记录缺失或不明确，说明尚未记录的内容，并在写入前确定落点。无需单独的状态文件或追溯迁移。

## 验收分级

默认情况下，每个工作目标都需要人工验收。项目可以在 `docs/coolflow.yml` 中声明 `acceptance.sensitive_paths`，把**低级别**改动的验收委托给证据：

```yaml
acceptance:
  sensitive_paths:
    - migrations/
    - src/auth/
```

**声明。** 该值必须是字符串列表，可以为空（`sensitive_paths: []`）；声明它就是人类的明确委托。如果文件缺失或无法解析、该键不存在，或值不是字符串列表，任何改动都不能定为 `low`；读取到无效值时应报告。条目包含 `*`、`?` 或 `[`，以 `/` 或 `./` 开头，或包含 `..` 时，声明同样无效。没有有效声明时，不要求定级，每个改动都需要人工验收。

**匹配。** 每个条目是相对仓库根目录的路径，匹配该文件或其下的任何内容；不支持 glob，并区分大小写。只要任何新增、修改、重命名、移动或删除的文件，其旧路径或新路径匹配某个条目，就算触及敏感路径。

**规则归人类所有。** 规则包括 `docs/coolflow.yml` 的 `acceptance` 节、本地文档标准的本节，以及 `AGENTS.md` 中的验收规则。Agent 不得新建、修改或删除其中任何部分，即使被要求也不行；它可以提出修改建议，由人类执行。唯一的例外是初始化，或经人类批准的采用或升级：此时可以从 CoolFlow 模板原样复制规则文本；`acceptance` 节本身始终由人类填写。

| 级别 | 适用条件 | 验收 |
| --- | --- | --- |
| `high` | 满足**任一**：修改持久数据或数据模式（schema）；涉及认证、授权、密钥、隐私或支付；有不可逆的外部副作用，例如发送消息、扣款或对外发布；修改 CI、发布或部署配置，或削弱某项检查；触及已声明的敏感路径。 | 人工验收，并具备恢复或缓解方案。 |
| `standard` | 既不是 `high` 也不是 `low`。典型情况：用户可见的行为发生变化，包括界面、API 约定、CLI 输出和提示信息；已验收的行为或验收条件发生变化；依赖发生变化。 | 人工验收。 |
| `low` | 满足下列**全部**条件。 | 无需人工检查；记录 `accepted_by_policy`。 |

只有同时满足以下全部条件，改动才是 `low`：

1. 存在有效声明，且不满足任何 `high` 条件。
2. 改动不触及 `docs/coolflow.yml`、本地文档标准，或任何层级的 Agent 指令文件，例如 `AGENTS.md`、`CLAUDE.md` 或 `.cursor/rules/`。
3. 用户可见的行为没有变化，`docs/features/` 或更早 Spec 中已验收的行为和验收条件没有被新增或修改。
4. 依赖清单和 lockfile 没有变化。
5. 现有测试、快照、fixture、测试辅助代码和测试配置没有被修改、重命名、移动、删除、跳过或排除；只新增测试。
6. 完整测试套件，以及 `AGENTS.md` 列出或 CI 强制执行的必需检查，在最终修订上一次运行全部通过；证据要标明是哪一次运行，例如本地命令输出或 CI 运行链接。
7. 有证据表明测试覆盖了改动的代码：提供该次运行的改动行覆盖率，或列出覆盖每个改动单元的测试，并附上它们在该次运行中的实际输出。

定级规则：

- 只有计划级别出现在早于任何实现改动的已提交修订中，目标才可能是 `low`。设计评审检查计划级别。
- Agent 可以提高已记录的级别，但不能降低；只有人类可以降低。拿不准时选更高级别。
- 记录 `accepted_by_policy` 前，必须对照最终 diff（而不是计划）逐条检查全部条件。最终 diff 指从开始实现前的修订到待验收修订的累计 diff，包括未提交的改动。这项检查由独立评审者执行，可以是全新上下文的 Agent 或人类；仅有实现 Agent 的自评不够。任何一条不满足，级别就上升。
- 在 `Delivery progress` 中记录最终级别、界定最终 diff 的两个修订、评审者和证据；Spec 中的 `Acceptance tier` 行记录计划级别。

定级之后：

- `accepted_by_policy` 不是人类决定，必须与 `accepted` 区分。任务结束报告中要列出所有以 `accepted_by_policy` 完成的目标。人类之后可以检查，并记录 `accepted` 或 `changes_requested`。
- `low` 改动没有用户可见的行为变化，因此很少影响 `docs/features/`。其他受影响的记录（例如架构）照常同步，工作照常归档，与人工验收后相同。
- 发布仍需单独的明确授权。
- 发现定级错误时，向人类提出如何通过[纠正层级](#纠正层级)收紧规则，例如增加敏感路径，或增加一项按已声明路径检查 diff 的 CI。只有人类可以修改规则；增加这类 CI 检查本身属于 `high` 改动。

## 记录 Agent Skills 产生的结果

当 Skill 产生值得保留的项目特定决策、发现或开放问题时，在授权范围内确定合适的项目文档，并
记录有用结果。先阅读项目本地文档规则和相关现有工作。在较长讨论中，必要时在有意义的检查点
更新；在完成任务前完成记录，不要依赖对话结束来触发后续写入。保留现有内容，并报告实际
更新了哪些文档。

根据内容和当前工作选择目标位置，并优先遵循项目本地约定；在没有本地约定时使用以下默认值：

- 发现阶段使用当前工作目标已有的笔记，或在有需要时使用 `docs/work/<objective>/brainstorm.md`。
  仅发现阶段不要求 Spec。
- 对于进入 Design Spec Loop 的选定目标，将相关需求、设计决策、取舍和开放问题记录到其统一的
  `docs/work/<objective>/spec.md` 或项目的等价文档。
- 将人类确认的、持久的项目级计划和决策，连同实际状态记录到相关的产品、Roadmap 或领域文档。
  Roadmap 可以总结未来功能范围，并标记为计划中或提议中；详细的未验收行为和未解决设计应留在
  工作记录或 Spec 中。人类验收后，按相关程度将受影响的已验收/当前事实同步到产品、Roadmap、
  领域和功能文档；验收不要求发布。

区分观察到的事实、用户陈述、决策、未验证的发现、假设和未解决问题。用户陈述可能无法独立验证。
尽可能更新现有权威记录，而不是重复内容；不要因为每次调用 Skill 就额外创建文档。如果用户要求
仅讨论结果、无法写入，或无法确定项目及合适目标，则不修改文档，并说明哪些内容尚未记录，以及
在已知时说明可存放的位置。必要时询问缺失的目标才能继续。

在骨架中创建 `docs/features/`、`docs/work/` 和 `docs/work/archive/`；如果 Git 目录为空，使用
`.gitkeep`。

## 工作产物（发现或开发期间创建）

## Idea → Brainstorm：竞争格局

在第 1 步，先明确问题、目标用户和使用情境，再研究现有解决方案。然后进行与决策相称的竞争格局
分析：

- 包含直接竞品、间接替代方案、替代品与用户当前的变通做法。
- 比较相关的目标用户、核心价值、用户体验、关键能力、定价/商业模式、用户反馈、局限性和尚未
  满足的需求。
- 使用可信来源；保留链接和研究日期，并区分观察到的事实、解释、假设和未知项。
- 综合判断是否存在有意义的机会或差异化。现有竞品可以验证需求；竞品存在本身并不否定一个想法。
  看不到竞品也不能证明需求存在。

对于小想法或窄功能，简要扫描或明确决定更深入研究价值不大，可能已经足够。对于新产品或不熟悉的
市场，则可能需要更深入的研究。这是一项探索活动，不是新阶段或强制关卡。

在有帮助时，将简明发现记录到当前工作的 `brainstorm.md`。只有当研究规模足够大、值得独立维护
时，才创建单独的 `competitive-landscape.md`。两者都不是每个想法必须创建的文档，也不会在项目
初始化时创建。

在发现阶段，**可以打开** `docs/work/<objective>/` 用于探索笔记和原型；此时不要求 Spec。当某个
目标被选定进入 **Design Spec Loop（第 6 步）** 时，创建默认的统一
`docs/work/<objective>/spec.md`。`<objective>` 是描述功能、MVP、修复或发布的有意义 slug 或
编号。初始产品旅程一旦开始发现，可以使用 `001-mvp`，但不要声称 MVP 范围已经确定。

完整的 Spec 应能被新的 Agent 理解，并提供：
- 背景、目标与非目标。
- 用户需求和具体的验收条件。
- 设计/架构决策及主要备选方案的取舍。
- 仓库布局：源代码、测试以及构建/运行命令所在的位置，位于 `docs/` 之外。
- 实施策略、依赖项和有意义的验证方法。
- 开放问题/假设，并明确与已决定内容区分。

### 何时使用工作模板

CoolFlow 为这些工作产物维护起始模板：

| 产物 | 何时使用 | 模板 |
| --- | --- | --- |
| `spec.md` | 默认的统一 Spec；当选定目标进入 Design Spec Loop（第 6 步）时创建，而不是仅在头脑风暴时创建。 | [Spec 模板](../templates/work/spec.md) |
| `prd.md` | 可选：当一个目标有较大的产品需求、用户旅程或范围，值得单独的产品文档时使用。 | [PRD 模板](../templates/work/prd.md) |
| `design.md` | 可选：当技术设计过于详细，不适合统一 Spec 时使用；从 Spec 链接过去。 | [详细设计模板](../templates/work/design.md) |
| `brainstorm.md` | 可选：真实发现工作开始后，作为第 1 步记录问题、用户、竞品、机会和假设的默认位置。 | [发现笔记模板](../templates/work/brainstorm.md) |
| `validation.md` | 可选：第 3 步或第 5 步产生实际验证证据和决定时使用。 | [验证记录模板](../templates/work/validation.md) |
| `tasks.md` | 可选：只有当任务进度必须在 Agent 会话、Agent 或时间之间持久保留，且现有跟踪方式不足时使用。 | [持久任务模板](../templates/work/tasks.md) |

这些模板是起点，不是检查清单。不要仅因为模板存在就创建可选产物。发现阶段按需使用笔记和原型；
只有选定的目标进入 Design Spec Loop 时，才编写统一 Spec。

可选产物，按实际需要创建：
- `prd.md`：可选，针对**一个开发目标**的较大产品需求——用户问题、旅程、范围和产品级成功标准；
  从 Spec 引用。它不是项目级 Product Brief。
- `design.md`：复杂的技术设计，过于详细而不适合统一 Spec；从 Spec 引用。
- `tasks.md`：**仅当**需要跨会话、Agent 或时间持久跟踪独立任务进度时使用。不要重复现有会话、
  Issue 或其他任务跟踪器。
- `brainstorm.md`：发现笔记、竞品发现、机会分析和产品假设。
- `competitive-landscape.md`：可选，值得独立维护的较完整竞品/市场研究；不要默认创建。
- `prototypes/`：作为验证证据使用的候选概念和可用原型。原型代码是一次性的：生产代码不得引用它，其构建或依赖配置也不得成为应用的配置。当原型方向被接受时，在第 7 步于 Spec 记录的源码树中实现，不要把原型就地扩展成应用。记录结论并将原型作为证据链接。
- `docs/architecture.md`：当前系统架构；`docs/adr/`：重要架构决策的理由。两者都是可选的，只有
  复杂性需要时才创建。
- `docs/feature-map.md`：用于操作已发布/已验收 UI 的实际导航路径、操作、稳定测试标识和验证
  流程；在有帮助时使用。它**不是** `features/` 的副本。

## 已验收知识与归档

- `docs/features/<feature>.md` 描述**实际已实现并验收**的行为，不是计划行为。未来想法保留在
  `roadmap.md` 或开放的工作 Spec 中。使用[功能记录模板](../templates/project/docs/features/feature-template.md)
  作为起点。
- 验收会触发相关当前文档的更新；它**不**意味着生产发布。
- 先同步已验收事实。然后将已完成的工作目录移动到 `docs/work/archive/`，选择性保留重要 Spec、
  设计/决策理由和验证证据；只有安全且适当时才清理临时草稿。
- 保留重要选择的出处。ADR 可以被取代，但不应被抹除。
- 永远不要假设空的模板意味着阶段已完成；`status: not_started` 和 `To decide` 表示尚未决定或
  尚未填写。
- 项目拥有自己的文档，可以自定义路径和约定。不强制固定上游版本，也不自动迁移。

## 可复用的项目 Solutions（可选）

`docs/solutions/` 是**已验证、应能帮助未来工作**的工程知识的可选位置。只有当项目有值得保留的
发现时才创建；它不是初始化骨架的一部分。参见 [Solutions 指南与模板](../templates/optional/solutions/README.md)。

当发现满足以下条件时，值得单独记录为 Solution：

1. **非显而易见：** 未来的开发者不太可能从最终代码、测试或普通文档中恢复重要推理。
2. **持久：** 在揭示它的那次变更之后，它仍应有用。
3. **有实质意义：** 忘记它可能导致重复失败、重大风险或大量重新发现。

Solution 可以记录已验证的根因与修复、技术约束、可复用的工程实践，或原本会被重复的失败方法。
每个文件聚焦一项发现，并链接到其来源工作、测试、提交或其他证据。先搜索是否已有重叠内容；
更新现有权威记录，而不是创建近似重复。

不要存储原始头脑风暴、每次调试记录、未验证的猜测，或代码和测试中已经显而易见的信息。只有在
发现经过验证、并且推理与证据仍可获得时才记录。在相关工作之前，只查阅与该任务相关的 Solutions。
当代码、依赖或外部条件使记录过时时，重新审视它们。

将知识保存在最窄的持久位置，并优先使用强制机制而不是文字（参见[纠正层级](#纠正层级)）：
- 架构、API、类型、Lint 规则、测试和断言：任何可以机械强制执行的约束。Agent 会模仿它读到的
  代码，因此用代码表达的约束比书面规则更能可靠地塑造后续工作。
- `docs/work/archive/`：已完成工作项中实际发生情况的历史证据。
- `docs/solutions/`：从经验中提取的可复用工程发现。
- `docs/adr/`：重要架构或技术决策为何做出。
- `AGENTS.md`：未来 Agent 必须一致遵循的稳定、高优先级指令。

代码注释不是知识的存放位置。Agent 会照抄注释，并用注释为变通做法辩护，因此注释往往在传播
hack，而不是解释它。通过命名、类型和测试表达意图；把理由保存在测试、ADR、Solution 或提交信息中。
不要添加注释，以下情况除外：工具指令、生成代码标记、许可证头，以及用于生成已发布 API 参考文档的
文档注释。本规则约束新代码：不要批量删除现有注释；项目已记录的、要求写注释的约定优先。

不要把经验沉淀变成每个功能或每次修复后的强制仪式。Evolution Loop 可以在任何阶段产生有用经验；
Solutions 是存储选项，不是额外的开发阶段。

这些 Solutions 是**项目本地**的。如果某项发现在多个项目中得到独立验证，可以提升到开发者的共享
知识库。只有经过广泛验证的开发原则才属于 CoolFlow 自己的 `methodology/` 或 `standards/`。

## 纠正层级

当一个缺陷或反复出现的纠正可能再次发生时，把修复放在能够承载它的最强层级：

1. **使其不可能：** 修改架构、API 或数据结构，使错误代码无法写出。
2. **使其失败：** 添加类型、Lint 规则、测试或 CI 检查来拒绝它。
3. **写下来：** 只有仍需判断的部分，才记录为 Solution 或 `AGENTS.md` 规则。

人工评审是最后一道防线，而不是机制本身。一次性错误不需要新规则。不要用文字重复已被强制执行的
约束；只有当推理不显而易见时才写 Solution，并在其中说明现在由什么强制执行它，或为什么无法强制执行。

## 架构决策记录（ADR，可选）

`docs/adr/` 保存**项目为何做出重要架构或技术决策**的持久记录。它不是通用决策日记，也不要求为
每个功能或实现选择创建。

当一个选择影响架构、数据所有权、系统边界、安全、部署、基础技术或难以撤销的依赖时，为每项决策
创建一条 ADR。有用的 ADR 通常记录背景、决策驱动因素、考虑过的选项、最终决策及其后果。参见
[ADR 模板与示例](../templates/optional/adr/README.md)。

使用连续、描述性的文件名，例如 `0001-use-expo-react-native.md`。保留已接受的记录。如果决策
改变，创建新的 ADR，并将旧记录标记为已被取代，而不是悄悄重写历史。当记录增多时，可选创建
README 索引进行总结。

ADR 记录决策的**理由**；当前系统设计属于 `architecture.md` 或相关 Spec。不要为常规 UI 细节、
变量命名、普通缺陷修复或每个功能创建 ADR。

## 文档所有权

- `product.md`（**Product Brief**）：*产品为何存在、为谁存在以及边界是什么*；`roadmap.md`：
  *何时/哪些范围*。
- 可选 `prd.md`：*这个特定增量需要什么用户可见结果*；它不是项目级 Product Brief。
- 统一 `spec.md`：*精确的预期行为 + 可实施的解决方案*。
- 可选 `design.md`：*由 Spec 引用的更深入技术细节*。
- 可选 `tasks.md`：*可变执行进度*，不是另一份需求来源。
- `features/`：*当前已验收且真实的行为*。
- `feature-map.md`：*在哪里以及如何操作/验证已实现功能*。
- 可选 `solutions/`：*哪些已验证工程经验应改变未来工作*。
- 可选 `adr/`：*重要架构或技术决策为何做出*。

## 对照 CoolFlow 审查

CoolFlow 合规审查以本规范或标明版本的离线快照为对照基准。读取项目本地规则，了解其实际文档职责、路径和约定。本规范允许的等效安排符合基准。分别报告与基准的差异和对项目已采用规则的违规。仅适用于初始化的要求只用于通过 CoolFlow 初始化的项目。对于考虑采用 CoolFlow 的已有项目，只建议有助于当前工作的改动，由用户决定是否采用及采用哪些。

随工具分发的快照是本规范的副本。修改本规范时，在同一改动中刷新快照。审查报告须标明使用的快照。

## AI 规则

1. 阅读相关文件，默认不要读取整个文档树。
2. 保留用户数据；未经批准，不要覆盖现有 README、AGENTS、代码或文档。
3. 信息未知时，在进展卡片中使用 `status: not_started`，在正文中使用 `To decide`；不要编造产品
   需求。
4. 产品关键决策询问人类；自动化可验证的文档/实现任务。
5. 当选定目标进入 **Design Spec Loop（第 6 步）** 时才创建统一 `spec.md`，而不是仅仅因为开始
   发现就创建；使用该 Loop 评审和修订重要设计，使用 **Implementation Loop（第 7 步）** 进行
   测试、代码评审和 Spec 一致性检查。**Evolution Loop** 可以在**任何步骤**由反馈、新想法或
   变化的需求触发，在产品假设、范围或方向需要重新考虑时返回任何相关步骤；常规质量修复仍留在
   局部 Loop 中。验收后，将持久文档同步作为一个**步骤**，而不是单独 Loop。发布和发布后反馈是
   可能发生的事件，不是 Evolution 的前提条件。
6. 在相关时，工作前查阅匹配的已验证 Solutions；只记录非显而易见、持久且有实质意义的发现。
   只有重要架构或技术决策才记录 ADR，而不是每个功能或修复。
7. 当一项纠正可能再次发生时，应用纠正层级：先通过架构、API、类型、Lint 规则、测试或 CI 检查
   强制执行，再考虑写 Solution 或 `AGENTS.md` 规则。除上文知识存放位置中列出的例外，不要添加代码注释。
8. 保持结构轻量；永远不要仅为满足检查清单而添加文件。
