# 文档规范（v0.1）

[English](documentation.md) | **简体中文**

**设计规则：** 将持久、已验收的项目知识与探索性、进行中的工作分开。**每个事实只保留一个权威
位置**；使用链接，而不是重复段落。

## 标准应用文档树

以下是用 CoolFlow 初始化的应用仓库的**默认文档树**。它描述推荐的项目文档位置与生命周期；
并不要求创建每一个可选文件。

```text
<app-repository>/
├── AGENTS.md                         # 初始化时必需
├── README.md                         # 初始化时必需
└── docs/
    ├── documentation.md              # 初始化时必需；本地文档规范
    ├── product.md                    # 初始化时必需
    ├── roadmap.md                    # 初始化时必需
    ├── domain.md                     # 初始化时必需
    ├── features/                     # 初始化时必需目录
    │   └── <feature>.md              # 已验收/当前行为；验收后添加
    ├── work/                         # 初始化时必需目录
    │   ├── <objective>/              # 仅在实际工作开始时创建
    │   │   ├── spec.md               # 目标进入 Design Spec Loop 时起草
    │   │   ├── prd.md                # 可选：较大的产品需求
    │   │   ├── design.md             # 可选：更深入的技术设计
    │   │   ├── tasks.md              # 可选：持久任务进度
    │   │   ├── brainstorm.md         # 可选：发现笔记与产品假设
    │   │   ├── competitive-landscape.md # 可选：较完整的竞品/市场研究
    │   │   └── prototypes/           # 可选：原型产物
    │   └── archive/                  # 初始化时必需目录
    │       └── <completed-work>/     # 选择性保留的已完成工作证据
    ├── solutions/                    # 可选：已验证、可复用的工程知识
    │   └── <solution>.md              # 每个文件聚焦一项发现
    ├── architecture.md               # 可选：当前系统架构
    ├── adr/                          # 可选：重要架构决策
    │   └── <number>-<decision>.md     # 每个文件一项决策
    └── feature-map.md                # 可选：实际 UI 导航与验证
```

### 各部分何时创建

| 位置 | 初始化时 | 发现/开发期间 | 验收后 |
|---|---|---|---|
| `AGENTS.md`、`README.md` | 缺失时创建 | 按需维护 | 保持最新 |
| `docs/documentation.md` | 缺失时复制完整本地规范 | 遵循并适配项目需要 | 保持项目约定最新 |
| `docs/product.md`、`roadmap.md`、`domain.md` | 创建模板；未知事实保持 `Not started` | 决策成为持久事实时更新 | 同步已验收变更 |
| `docs/features/` | 创建目录 | 通常保持不变 | 添加或更新已验收功能描述 |
| `docs/work/` | 创建目录 | 发现阶段有需要时打开目标目录；进入 Design Spec Loop 时创建其 `spec.md` | 选择性归档 |
| `docs/work/archive/` | 创建目录 | 无需填充 | 保留有用的历史证据 |
| `docs/solutions/` | 默认不创建 | 只有在验证了非显而易见、持久且有实质意义的工程发现时创建 | 保持有用发现最新；删除误导或过时内容 |
| `docs/adr/` | 默认不创建 | 当重要的架构或技术决策需要持久理由时，创建一条记录 | 保留历史；用新 ADR 取代旧决策，而不是重写旧记录 |
| 可选文档 | 默认不创建 | 只有复杂性或真实需要证明其价值时才添加 | 相关时维护或归档 |

**初始化时必需** 是指在模板骨架中创建缺失的文件/目录。它不表示要编造内容、创建空的功能文档，
或开始一个实施目标。

**在发现阶段**，目标目录可以只放笔记或原型，不写 Spec。**当选定的目标进入 Design Spec Loop**
时，编写其统一的 `spec.md`，定义可实施的设计与验证标准。仅仅进行头脑风暴并不要求 Spec；可选
产物不是固定检查清单。

### 这棵文档树刻意不规定什么

- CoolFlow v0.1 不要求默认创建 `docs/solutions/`、`docs/adr/`、`docs/knowledge/` 或
  `docs/state.md`。
- `docs/solutions/` 是已验证、可复用工程知识的推荐可选位置。它不在初始化时创建。
- `docs/adr/` 是架构决策记录（ADR）的可选位置：每个文件一项重要决策。它不在初始化时创建。
- CoolFlow 自己的 `flowecosystem/` 目录属于 **CoolFlow 方法论仓库**。它收录外部框架与方法，
  不会被复制到应用仓库。应用的 `docs/solutions/` 是它自己的工程知识库；两者名称相关，但用途
  不同。
- 项目可以在初始化后自定义文档名称和位置。每个事实保留一个权威位置，并保持项目本地
  `AGENTS.md` / README 导航准确。

## 记录 Agent Skills 产生的结果

当 Skill 产生值得保留的项目特定决策、发现或开放问题时，在授权范围内确定合适的项目文档，并
记录有用结果。先阅读项目本地文档规则和相关现有工作。在较长讨论中，必要时在有意义的检查点
更新；在完成任务前完成记录，不要依赖对话结束来触发后续写入。保留现有内容，并报告实际
更新了哪些文档。

根据内容和当前工作选择目标位置，并优先遵循项目本地约定；在没有本地约定时使用以下默认值：

- 发现阶段使用当前工作目标已有的笔记，或在有需要时使用 `docs/work/<objective>/brainstorm.md`。
  仅发现阶段不要求 Spec。
- 对于进入 Design Spec Loop 的选定目标，将相关需求、设计决策、取舍和开放问题记录到其统一的
  `docs/work/<objective>/spec.md` 或项目的等价文档。
- 将人类确认的、持久的项目级计划和决策，连同实际状态记录到相关的产品、Roadmap 或领域文档。
  Roadmap 可以总结未来功能范围，并标记为计划中或提议中；详细的未验收行为和未解决设计应留在
  工作记录或 Spec 中。人类验收后，按相关程度将受影响的已验收/当前事实同步到产品、Roadmap、
  领域和功能文档；验收不要求发布。

区分观察到的事实、用户陈述、决策、未验证发现、假设和未解决问题。用户陈述可能无法独立验证。
尽可能更新现有权威记录，而不是重复内容；不要因为每次调用 Skill 就额外创建文档。如果用户要求
仅讨论结果、无法写入，或无法确定项目及合适目标，则不修改文档，并说明哪些内容尚未记录，以及
在已知时说明可存放的位置。必要时询问缺失的目标才能继续。

## 核心项目文档（初始化时创建）

| 路径 | 用途 |
| --- | --- |
| `AGENTS.md` | 自包含的简明生命周期与工作边界；引用本地文档规范 |
| `README.md` | 面向人类阅读的项目入口；不编造功能 |
| `docs/documentation.md` | 完整的项目本地文档规范；初始化后独立维护 |
| `docs/product.md` | 简明的项目级 Product Brief：问题、受众、愿景、价值、边界和当前定位；**不是 PRD** |
| `docs/roadmap.md` | MVP、未来版本与优先级；明确区分计划与已验收 |
| `docs/domain.md` | 统一语言、领域边界、核心规则；暂定，初期可以保持未填写 |

在骨架中创建 `docs/features/`、`docs/work/` 和 `docs/work/archive/`；如果 Git 目录为空，使用
`.gitkeep`。

## 工作产物（发现或开发期间创建）

## Idea → Brainstorm：竞争格局

在第 1 步，先明确问题、目标用户和使用情境，再研究现有解决方案。然后进行与决策相称的竞争格局
分析：

- 包含直接竞品、间接替代方案、替代品与用户当前的变通做法。
- 比较相关的目标用户、核心价值、用户体验、关键能力、定价/商业模式、用户反馈、局限性和尚未
  满足的需求。
- 使用可信来源；保留链接和研究日期，并区分观察到的事实、解释、假设和未知项。
- 综合判断是否存在有意义的机会或差异化。现有竞品可以验证需求；竞品存在本身并不否定一个想法。
  看不到竞品也不能证明需求存在。

对于小想法或窄功能，简要扫描或明确决定更深入研究价值不大，可能已经足够。对于新产品或不熟悉的
市场，则可能需要更深入的研究。这是一项探索活动，不是新阶段或强制关卡。

在有帮助时，将简明发现记录到当前工作的 `brainstorm.md`。只有当研究规模足够大、值得独立维护
时，才创建单独的 `competitive-landscape.md`。两者都不是每个想法必须创建的文档，也不会在项目
初始化时创建。

在发现阶段，**可以打开** `docs/work/<objective>/` 用于探索笔记和原型；此时不要求 Spec。当某个
目标被选定进入 **Design Spec Loop（第 6 步）** 时，创建默认的统一
`docs/work/<objective>/spec.md`。`<objective>` 是描述功能、MVP、修复或发布的有意义 slug 或
编号。初始产品旅程一旦开始发现，可以使用 `001-mvp`，但不要声称 MVP 范围已经确定。

完整的 Spec 应能被新的 Agent 理解，并提供：
- 背景、目标与非目标。
- 用户需求和具体的验收条件。
- 设计/架构决策及主要备选方案的取舍。
- 实施策略、依赖项和有意义的验证方法。
- 开放问题/假设，并明确与已决定内容区分。

### 何时使用工作模板

CoolFlow 为这些工作产物维护起始模板：

| 产物 | 何时使用 | 模板 |
| --- | --- | --- |
| `spec.md` | 默认的统一 Spec；当选定目标进入 Design Spec Loop（第 6 步）时创建，而不是仅在头脑风暴时创建。 | [Spec 模板](../templates/work/spec.md) |
| `prd.md` | 可选：当一个目标有较大的产品需求、用户旅程或范围，值得单独的产品文档时使用。 | [PRD 模板](../templates/work/prd.md) |
| `design.md` | 可选：当技术设计过于详细，不适合统一 Spec 时使用；从 Spec 链接过去。 | [详细设计模板](../templates/work/design.md) |
| `tasks.md` | 可选：只有当任务进度必须在 Agent 会话、Agent 或时间之间持久保留，且现有跟踪方式不足时使用。 | [持久任务模板](../templates/work/tasks.md) |

这些模板是起点，不是检查清单。不要仅因为模板存在就创建可选产物。发现阶段按需使用笔记和原型；
只有选定的目标进入 Design Spec Loop 时，才编写统一 Spec。

可选产物，按实际需要创建：
- `prd.md`：可选，针对**一个开发目标**的较大产品需求——用户问题、旅程、范围和产品级成功标准；
  从 Spec 引用。它不是项目级 Product Brief。
- `design.md`：复杂的技术设计，过于详细而不适合统一 Spec；从 Spec 引用。
- `tasks.md`：**仅当**需要跨会话、Agent 或时间持久跟踪独立任务进度时使用。不要重复现有会话、
  Issue 或其他任务跟踪器。
- `brainstorm.md`：发现笔记、竞品发现、机会分析和产品假设。
- `competitive-landscape.md`：可选，值得独立维护的较完整竞品/市场研究；不要默认创建。
- `prototypes/`：候选概念和可用原型，放在适用的工作目录中。
- `docs/architecture.md`：当前系统架构；`docs/adr/`：重要架构决策的理由。两者都是可选的，只有
  复杂性需要时才创建。
- `docs/feature-map.md`：用于操作已发布/已验收 UI 的实际导航路径、操作、稳定测试标识和验证
  流程；在有帮助时使用。它**不是** `features/` 的副本。

## 已验收知识与归档

- `docs/features/<feature>.md` 描述**实际已实现并验收**的行为，不是计划行为。未来想法保留在
  `roadmap.md` 或开放的工作 Spec 中。使用[功能记录模板](../templates/project/docs/features/feature-template.md)
  作为起点。
- 验收会触发相关当前文档的更新；它**不**意味着生产发布。
- 先同步已验收事实。然后将已完成的工作目录移动到 `docs/work/archive/`，选择性保留重要 Spec、
  设计/决策理由和验证证据；只有安全且适当时才清理临时草稿。
- 保留重要选择的出处。ADR 可以被取代，但不应被抹除。
- 永远不要假设空的模板意味着阶段已完成；`Not started` 表示尚未决定或尚未填写。
- 项目拥有自己的文档，可以自定义路径和约定。不强制固定上游版本，也不自动迁移。

## 可复用的项目 Solutions（可选）

`docs/solutions/` 是**已验证、应能帮助未来工作**的工程知识的可选位置。只有当项目有值得保留的
发现时才创建；它不是初始化骨架的一部分。参见 [Solutions 指南与模板](../templates/optional/solutions/README.md)。

当发现满足以下条件时，值得单独记录为 Solution：

1. **非显而易见：** 未来的开发者不太可能从最终代码、测试或普通文档中恢复重要推理。
2. **持久：** 在揭示它的那次变更之后，它仍应有用。
3. **有实质意义：** 忘记它可能导致重复失败、重大风险或大量重新发现。

Solution 可以记录已验证的根因与修复、技术约束、可复用的工程实践，或原本会被重复的失败方法。
每个文件聚焦一项发现，并链接到其来源工作、测试、提交或其他证据。先搜索是否已有重叠内容；
更新现有权威记录，而不是创建近似重复。

不要存储原始头脑风暴、每次调试记录、未验证的猜测，或代码和测试中已经显而易见的信息。只有在
发现经过验证、并且推理与证据仍可获得时才记录。在相关工作之前，只查阅与该任务相关的 Solutions。
当代码、依赖或外部条件使记录过时时，重新审视它们。

将知识保存在最窄的持久位置：
- `docs/work/archive/`：已完成工作项中实际发生情况的历史证据。
- `docs/solutions/`：从经验中提取的可复用工程发现。
- `docs/adr/`：重要架构或技术决策为何做出。
- 测试、类型和断言：可通过机械方式强制执行的行为。
- 代码注释：某条代码路径旁所需的局部理由。
- `AGENTS.md`：未来 Agent 必须一致遵循的稳定、高优先级指令。

不要把经验沉淀变成每个功能或每次修复后的强制仪式。Evolution Loop 可以在任何阶段产生有用经验；
Solutions 是存储选项，不是额外的开发阶段。

这些 Solutions 是**项目本地**的。如果某项发现在多个项目中得到独立验证，可以提升到开发者的共享
知识库。只有经过广泛验证的开发原则才属于 CoolFlow 自己的 `methodology/` 或 `standards/`。

## 架构决策记录（ADR，可选）

`docs/adr/` 保存**项目为何做出重要架构或技术决策**的持久记录。它不是通用决策日记，也不要求为
每个功能或实现选择创建。

当一个选择影响架构、数据所有权、系统边界、安全、部署、基础技术或难以撤销的依赖时，为每项决策
创建一条 ADR。有用的 ADR 通常记录背景、决策驱动因素、考虑过的选项、最终决策及其后果。参见
[ADR 模板与示例](../templates/optional/adr/README.md)。

使用连续、描述性的文件名，例如 `0001-use-expo-react-native.md`。保留已接受的记录。如果决策
改变，创建新的 ADR，并将旧记录标记为已被取代，而不是悄悄重写历史。当记录增多时，可选创建
README 索引进行总结。

ADR 记录决策的**理由**；当前系统设计属于 `architecture.md` 或相关 Spec。不要为常规 UI 细节、
变量命名、普通缺陷修复或每个功能创建 ADR。

## 文档所有权

- `product.md`（**Product Brief**）：*产品为何存在、为谁存在以及边界是什么*；`roadmap.md`：
  *何时/哪些范围*。
- 可选 `prd.md`：*这个特定增量需要什么用户可见结果*；它不是项目级 Product Brief。
- 统一 `spec.md`：*精确的预期行为 + 可实施的解决方案*。
- 可选 `design.md`：*由 Spec 引用的更深入技术细节*。
- 可选 `tasks.md`：*可变执行进度*，不是另一份需求来源。
- `features/`：*当前已验收且真实的行为*。
- `feature-map.md`：*在哪里以及如何操作/验证已实现功能*。
- 可选 `solutions/`：*哪些已验证工程经验应改变未来工作*。
- 可选 `adr/`：*重要架构或技术决策为何做出*。

## AI 规则

1. 阅读相关文件，默认不要读取整个文档树。
2. 保留用户数据；未经批准，不要覆盖现有 README、AGENTS、代码或文档。
3. 信息未知时，标记为 `Not started` / `To decide`；不要编造产品需求。
4. 产品关键决策询问人类；自动化可验证的文档/实现任务。
5. 当选定目标进入 **Design Spec Loop（第 6 步）** 时才创建统一 `spec.md`，而不是仅仅因为开始
   发现就创建；使用该 Loop 评审和修订重要设计，使用 **Implementation Loop（第 7 步）** 进行
   测试、代码评审和 Spec 一致性检查。**Evolution Loop** 可以在**任何步骤**由反馈、新想法或
   变化的需求触发，在产品假设、范围或方向需要重新考虑时返回任何相关步骤；常规质量修复仍留在
   局部 Loop 中。验收后，将持久文档同步作为一个**步骤**，而不是单独 Loop。发布和发布后反馈是
   可能发生的事件，不是 Evolution 的前提条件。
6. 在相关时，工作前查阅匹配的已验证 Solutions；只记录非显而易见、持久且有实质意义的发现。
   只有重要架构或技术决策才记录 ADR，而不是每个功能或修复。
7. 保持结构轻量；永远不要仅为满足检查清单而添加文件。
