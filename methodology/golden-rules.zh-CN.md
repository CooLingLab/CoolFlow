# CoolFlow Golden Rules · 中文版

[English](golden-rules.md) | **简体中文**

**The Four Golden Rules for AI-Assisted Software Development**  
*By Cooling · Creator of CoolFlow*

**灵感来自空客飞行员金科玉律（Airbus Golden Rules for Pilots）。** Cooling 将航空 SOP 对优先级、态势感知、恢复能力和实际验证的重视，应用到人类主导的 AI 软件开发。**这些是 CoolFlow 独立提出的软件工程原则，并非空客官方规范或获得空客认可的标准。** 不使用完整的 CoolFlow 方法论，也可以独立遵循。

> **适用对象：人类开发者。** 即使大量工作交给 AI Agent，人仍应理解、验证并掌握整个软件开发生命周期。
>
> Golden Rules 是长期有效的**判断原则**，不是强制的新阶段、自动关卡、Skill 或 `AGENTS.md` 的替代品。

## 1. Keep It Working → Ship Small → Improve

**保持正确运行 → 小步交付 → 持续改进**

当工程目标出现冲突时，默认按照以下优先级：

1. **Keep It Working：** 保护已经验证的正确行为、用户数据、安全性和关键功能。出现严重回归或重大风险时，优先处理，避免在错误基础上不断堆叠新代码。
2. **Ship Small：** 相比猜测未来需要的大范围功能，优先交付**最小、完整、有价值、可验证**的增量。这里的「交付」不允许跳过必要测试、审查或发布前的检查。
3. **Improve：** 在功能与交付路径可靠的基础上，继续改善性能、架构、可维护性、体验或功能范围。

**这是一条处理优先级冲突的原则，并不是三个必须按顺序完成的开发阶段。** 全新项目没有已有功能需要修复，可以先建立最小可运行基线；紧急的安全或性能问题也可能自然成为当前最优先的交付内容。**Ship Small 不是 Ship More**：正确性与价值比产出数量重要。

**人的检查问题：** 是否保护了已有正确结果？是否优先交付最小、有意义的增量？是否避免了无谓扩张？

## 2. Know the Actual State

**始终知晓项目与 Agent 的实际状态**

应严格区分：开发者**计划**什么、Agent **尝试**了什么、仓库或环境**实际变化**了什么、哪些已经**验证**、哪些已经**人工验收**、哪些已**正式发布**。计划和 AI 的完成声明都不能直接当作实际进度。

对于重要任务，Agent 可以在结束时报告当前目标和 Flow / Loop、实际修改、验证证据、已知障碍以及下一步。但报告只能作为**线索**，不能替代 Spec、Git 历史与差异、测试结果和人工验收记录等证据。

不同开发目标可能同时处在不同阶段，不能为了展示方便而虚构整个项目只有一个阶段。

未来可以按需建立项目状态文档或 Dashboard，但**这条原则不强制要求**。如果建立状态视图，应显示依据和最后核实时间，避免过时状态误导人。

**人的检查问题：** 我是否知道真正发生了什么、什么还没有验证，以及下一步应当做什么？

## 3. Keep a Way Back

**始终保留可恢复的退路**

在重要变更之前，理解可能影响的范围，并保留回到可靠状态的实际办法。根据风险使用适当的 Git 分支、提交记录、隔离环境、备份和恢复手段；恢复流程本身也应在必要时得到验证。

**Git 可以恢复代码历史，但不能保证恢复生产数据库、用户数据、已删除的密钥、外部副作用或已经执行的迁移。** 不可逆操作需要单独评估风险，并设计恢复或缓解措施。未经过验证的回退方案未必可靠。

**人的检查问题：** 这次修改可能破坏什么？可靠的基准版本在哪里？失败时能真正恢复吗？

## 4. Prove It Works

**以真实结果证明有效**

不能仅凭 Agent 自述已完成、文件已生成或编译成功，就认定预期结果已经实现。

应提供适合任务的**直接、可复查的证据**：真实操作的用户流程、相关测试、日志、截图、模拟器或真机运行结果、外部可观察的副作用，以及与验收标准的对照。在有必要时，保存命令、输入和测试结果，便于他人重复验证。

始终明确区分**未测试、测试通过、人工验收和正式发布**。

本条还借鉴了 PStack 的 [Prove It Works](https://github.com/cursor/plugins/tree/main/pstack/skills/principle-prove-it-works)。CoolFlow 将其作为贯穿 Flow 和 Loops 的人工验收原则，不要求安装 PStack。

**人的检查问题：** 有什么可观察的证据能证明这个结果？还有什么没有经过验证？

## 四条原则分别解决什么问题？

| 维度 | Golden Rule | 核心问题 |
| --- | --- | --- |
| 工程优先级 | Keep It Working → Ship Small → Improve | 发生冲突时，什么优先？ |
| 态势感知 | Know the Actual State | 实际发生了什么，而不是计划做什么？ |
| 恢复能力 | Keep a Way Back | 失败后能否恢复到安全状态？ |
| 证据与验收 | Prove It Works | 如何证明成果真正有效？ |

四条原则贯穿 [Development Flow](flow.md) 和 [Design Spec、Implementation、Evolution Loops](loops.md)，但不要求人类亲自写每一行代码或管理每一次 Agent 操作。

## 与 AGENTS.md 的分工

- **Golden Rules：** 面向**人类开发者**的判断原则。
- **Flow 和 Loops：** 推荐的软件开发过程与反馈机制。
- **AGENTS.md：** 面向 **AI Agent** 的明确执行规则、授权边界、验证与报告约定。
- **Skills 与工具：** 可选的重复任务执行和自动化机制。

不要机械地把 Golden Rules 转化成额外强制文档、全局状态文件、Skills 或每轮对话必填的报告。开发者可以在有实际需求时，另行制定适合项目的 Agent 指令。
