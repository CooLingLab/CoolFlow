# CoolFlow 循环：三个自适应反馈周期

[English](loops.md) | **简体中文**

CoolFlow 有**一条开发流程**和**三个自适应循环（Adaptive Loops）**：

- **Design Spec Loop（第 6 步）：** 通过 Spec、评审和修订提升设计质量。
- **Implementation Loop（第 7 步）：** 通过代码、测试、评审和修复提升实现质量。
- **Evolution Loop（跨阶段）：** 从**任何步骤**重新评估反馈、新想法或变化的需求，并按需调整
  **任何相关步骤**。它没有强制的入口或终点。

前两个循环主要对应各自命名的阶段；第三个循环是**跨阶段**的，不是强制的发布后周期。这些是
反馈机制，**不是 Agent 编排、固定阶段关卡，也不要求无限迭代**。**Documentation Sync 是验收后
的步骤，不是第四个循环。**

## 1. Design Spec Loop — 设计质量

`Draft → Review → Refine ↻`

**目标：** 让通过 Spec 表达的设计清晰、正确且可实施。

- 当选定的目标进入本循环时，起草其统一的 `spec.md`；此前的发现阶段可以使用工作目录而不写 Spec。
  Spec 承载背景、目标/非目标、行为与验收条件、技术决策、取舍、实施策略和验证。可选的 PRD 或
  详细设计可以链接进来，而不重复内容。
- 独立评审最好使用全新上下文。评审者阅读**当前 Spec 草稿**、链接的参考资料和相关**现有代码**，
  而不是继承起草者的假设。
- 查找遗漏的案例、有风险的假设、过度设计、不兼容问题、可行性问题和不清楚的实施步骤。
- 修订 Spec，并验证重要阻塞项已解决。产品关键取舍由人类决定。
- EGM Goldfish 是**推荐的可选**评审方法，不是依赖项。
- 阅读现有代码以检查设计可行性，**不同于**评审本任务新产生的代码。
- `tasks.md` 是可选的，仅在需要超出 Agent 会话或现有任务系统的持久进度跟踪时使用。

**退出条件：** 设计已得到与任务风险相称的充分评审、前后一致，并准备进入实施。

## 2. Implementation Loop — 代码质量

`Build → Test → Review → Fix ↻`

**目标：** 实现已批准的行为，并取得其确实可用的证据。

- 编码 Agent 通常在自己的会话中管理任务；CoolFlow 不要求持久任务文件。
- 运行相关测试，并评审变更代码的正确性、安全性、可维护性和回归风险。
- 对照**已批准的 Spec 和验收条件**检查实现，而不仅仅是测试套件。
- 当代码与 Spec 出现分歧时，判断是实现错误，还是需求需要人类重新考虑。
- 如果 Spec 不完整或有缺陷，**返回 Design Spec Loop**。绝不要为了让有问题的代码显得合理而
  悄悄改写需求。
- 在已批准的行为和约束内自主工作。当继续推进将改变产品意图、实质性扩大范围，或承诺一个重要的
  未决取舍时，暂停等待人类判断；呈现证据和需要做的决定，而不是悄悄决定。
- 重复直到证据支持人类验收，或报告尚未解决的阻塞项。

**退出条件：** 经过测试和评审的实现已准备好进入人类验收决定。

## 验收后步骤 — Documentation Sync 与归档（不是循环）

`Human Acceptance → 同步已接受事实 → 验证文档一致性 → 选择性归档 →（单独授权发布）→ 适用时执行并验证发布`

- `docs/features/` 描述已验收的实际行为，而不是推测性的设计。
- 仅在受影响时更新 `product.md`、`domain.md`、`roadmap.md`、`architecture.md`、`feature-map.md`。
- 保留重要的历史 Spec、决策和验证证据；在适当时删除冗余的临时草稿。
- 验收可能先于生产发布，因此要准确记录发布状态。
- 项目的文档规范可以在初始化后独立演进。

## 3. Evolution Loop — 跨阶段适应

`New Input → Reassess → Adapt ↻`

**目标：** 针对反馈、新想法或变化的需求，在**实施和发布之前、期间或之后**，重新评估并在确有
必要时调整产品方向、范围或重要决策。

- Evolution Loop 可以**从八个步骤中的任何一步开始**，并**重新进入任何相关步骤**。它不需要
  先有发布、Roadmap 更新或固定顺序。
- 示例：第 3 阶段的概念原型推翻了目标用户假设，因此回到第 1 步；第 5 阶段的 UI 设计暴露了
  领域理解错误，因此回到第 2 步；第 7 阶段的实现暴露了产品范围问题，因此回到第 4 步；第 8 步
  之后的用户反馈可以导致回到任何相关的前序步骤。
- 新输入可以是一个问题、功能请求、新想法，或某个功能变得过时。重新评估可以导致行动、继续观察，
  或决定不采纳该输入。
- 只重新审视受该输入影响的决策和产物。不要机械地重跑全部八个阶段。
- **区分局部质量迭代与产品演进：** 在已商定需求内修复测试或修订设计，属于 Implementation 或
  Design Spec Loop。只有当学习结果值得重新思考假设、范围或方向时，才使用 Evolution Loop。
- 产品关键变更仍由人类判断负责。没有强制终点；根据所学内容停止、继续或转向。

## 评审术语

| 评审 | 对象 | 时机 |
| --- | --- | --- |
| Design Spec Review（EGM 风格） | 通过 Spec 表达的设计、假设、可行性和实施策略 | 大规模编码之前 |
| Code Review | 新变更的代码与测试 | 编码之后，在 Implementation Loop 内 |
| Spec Conformance | 预期行为与实际实现 | Implementation Loop 内以及验收时 |
| Scenario Review | **CoolFlow 自身**：Agent 是否正确遵循标准？ | CoolFlow 内部验证，位于 `flowreviews/scenarios/`；保留在源仓库，不复制到目标应用 |

不要将 CoolFlow 内部的 **Scenario Review** 误认为产品开发的第四个循环。
