# CoolFlow 生命周期（推荐流程）

[English](flow.md) | **简体中文**

人类开发者的总体优先事项由 [Golden Rules](golden-rules.zh-CN.md) 描述。这些规则指导每个阶段的
决策，但不新增阶段，也不要求必须产出特定文档。

CoolFlow 描述的是**一条灵活的开发流程和三个自适应循环**，而不是固定的阶段调度器。
**Evolution Loop 可以从任何阶段触发**：当反馈、新想法或需求变化要求重新考虑产品决策时，它可以
返回任何相关阶段。每个阶段只建议产出和问题；开发者与 Agent 自行决定哪些内容有价值。不需要
流程引擎、状态转换或关卡文件。

| 阶段 | 目的 | 典型结果 |
| --- | --- | --- |
| 1. Idea → Brainstorm | 明确问题、用户与价值；分析竞争格局；识别机会并形成可验证的产品假设 | 持续演进的 `product.md`；当前工作中适当规模的市场/竞品发现与探索笔记 |
| 2. Lightweight strategic DDD | 建立暂定的战略领域模型：统一语言、语义边界和核心业务规则；战术设计属于第 6 步 | `domain.md` |
| 3. Concept Prototype → Validation | 用限时原型、技术 spike 或其他相称方法验证最危险的假设；不是 MVP | `work/<objective>/prototypes/` 下的原型、spike 或其他验证证据 |
| 4. Roadmap | 定义产品级 MVP/当前版本、非目标与后续方向；不是功能或任务计划 | `roadmap.md`；范围较大的产品可选 PRD |
| 5. UI Prototype | 设计当前版本的关键流程、视觉方向、关键界面与状态；在有用时进行用户验证 | 相关工作目录中的原型、视觉方向与笔记 |
| 6. Design Spec Loop | 记录需求、验收条件、方案、可选战术领域设计、实施与验证策略；评审并修订 | `work/<objective>/spec.md`；可选 `design.md` |
| 7. Implementation Loop | 小步实现、测试行为、评审变更代码与 Spec 一致性、修复并记录证据（通常由 Agent 辅助） | 经测试的代码、评审证据与已知风险；除非需要持久跟踪，否则任务保存在 Agent 会话中 |
| 8. Human Acceptance → Documentation Sync → Release | 人类验收实际行为；同步持久文档；归档有意义的历史；发布并学习 | 视情况更新 `features/`、domain/roadmap/feature-map；`work/archive/` |

## 第 1 步 — Idea → Brainstorm

目标不是把每个想法立即变成开发计划。先理解问题和用户，再考察该需求目前如何被满足，识别可信的
机会，并形成产品假设。

一个有用的顺序是：

1. **问题与用户发现** — 明确谁在什么情境下遇到问题、问题有多重要，以及用户需要什么结果。
   当证据不足时，进行与决策相称的用户研究——访谈、观察或现有数据——并区分观察事实、用户陈述、
   解释和假设。避免过早定义解决方案。
2. **竞争格局分析** — 研究解决相同或相邻问题的现有方式：
   - **直接竞品：** 为相似用户解决相似核心任务的产品。
   - **间接替代方案：** 用不同方式解决该需求的产品。
   - **替代品与变通做法：** 线下方法、通用工具、电子表格、社区，或用户目前依赖的组合方案。
   - 只比较与决策相关的维度：目标用户、核心价值、主要体验、关键能力、定价/商业模式、用户反馈、
     局限性以及尚未满足的需求。
3. **机会识别** — 综合现有方案做得好的地方、用户遇到的摩擦、哪些人群或用例仍未得到充分服务，
   以及是否存在有意义的机会。现有竞品可以验证需求；竞品存在本身并不否定一个想法。看不到竞品
   也不能单独证明存在需求。
4. **产品假设** — 说明打算构建什么、为谁构建、解决什么问题、为什么所提方法可能更好或有意义地
   不同，以及还有哪些假设需要验证。

研究深度与决策相称。一个小想法或窄功能可能只需要快速扫描，甚至不需要单独研究；新产品或不熟悉
的市场则可能需要更深入的分析。使用可信、最好是一手的来源；记录链接和研究日期，并区分观察到
的事实、解释、假设和未知项。不要把功能清单当作市场验证，也不要编造竞品细节。

在有帮助时，将简明的发现和链接记录到当前工作的 `brainstorm.md`。只有当研究规模足够大、需要
独立维护时，才创建单独的 `competitive-landscape.md`。两者都不是每个想法必须创建的文档。这是
一项探索活动，不是新阶段或固定关卡。

**第 6 阶段并不要求运行 EGM。** 对于复杂、风险高或不熟悉的工作，可以使用独立的设计评审 Agent；
对于小修复，简明的 Spec/检查清单可能已经足够。

**Human Acceptance 与 Release 不同。** 验收后，Documentation Sync 会更新当前项目事实，并选择性
归档工作；它**不是**独立的顶层循环。已验收但尚未发布的行为必须被准确描述，包括相关发布状态。

对于新应用，第一个工作目标可以是 `work/001-mvp/`，**在发现阶段有需要时创建**（不是在文件夹
初始化时创建）。发现笔记和原型可以放在其中而不需要 Spec；当选定目标进入 **Design Spec Loop
（第 6 步）** 时，再编写统一的 `spec.md`。目录标签不预设 MVP 范围已经确定。

**Evolution Loop（跨阶段）：** 新输入 → 重新评估 → 适应。在**任何步骤**，反馈、新想法或需求
变化都可能促使重新考虑产品方向、范围或关键决策，并返回**任何相关步骤**。例如，第 3 阶段失败的
概念原型可能返回 Brainstorm（第 1 步）；第 7 阶段实现期间发现的无效产品假设可能需要重新审视
Roadmap（第 4 步）。发布后的反馈只是触发条件之一，**不是前提条件**。普通的设计或代码修正仍
留在对应的局部质量循环中。永远不要要求固定的起点/终点、自动修订 Roadmap，或机械地重复全部
八个阶段。

参见[质量循环](loops.zh-CN.md)和[文档规则](../standards/documentation.zh-CN.md)。
