# 阶段活动与 Skill 边界

[English](activities.md) | **简体中文**

**状态：讨论稿。** 本文是[开发流程](flow.zh-CN.md)的非规范性配套文档。它识别每个阶段中可能出现的不同活动，以及在边界达成一致后，哪些位置可能适合使用 Skill。

本文不新增阶段，不要求每个项目执行所有活动，也不替代[文档规范](../standards/documentation.zh-CN.md)。八个阶段和三个 Adaptive Loops 仍以 [flow.zh-CN.md](flow.zh-CN.md) 的定义为准。

## 本文档的推进方式

活动逐个阶段与开发者确认。阶段经过讨论并确认前，其内容标记为 `讨论中` 或 `尚未开始`。已确认的活动清单是双方对工作的共同理解，不是强制检查表。

每个已确认阶段使用同一张表：

- **活动：** 阶段内一项独立的工作。
- **回答的问题：** 该活动要解决的问题。
- **核心产出：** 该活动产生的结果或证据。
- **边界：** 哪些属于本活动，哪些属于相邻活动。

在所有阶段边界达成一致前，刻意不分配 Skill。

## 1. Idea → Brainstorm

状态：`已确认`（2026-11-05）

| ID | 活动 | 回答的问题 | 核心产出 | 边界 |
| --- | --- | --- | --- | --- |
| 1.1 | 理解用户与问题（含与决策相称的用户研究） | 谁在什么情境下遇到什么困难？ | 用户、场景、问题、已知证据，以及收集证据时的方法、来源和日期 | 不研究竞品，不提出方案 |
| 1.2 | 研究竞品与替代方案 | 这个问题目前是如何被解决的？ | 直接竞品、间接替代方案、变通做法、来源与研究日期 | 不决定我们要做什么，也不把竞品功能当作需求 |
| 1.3 | 定义问题边界 | 我们要解决哪个问题，不解决哪些问题？ | 问题陈述、目标用户边界、非目标与关键约束 | 不判断机会是否值得，也不设计方案 |
| 1.4 | 评估机会 | 现有方案的哪些缺口值得考虑，依据是什么？ | 机会假设、支持证据、反证与未知项 | 不承诺开发，也不展开功能 |
| 1.5 | 发散产品方向 | 有哪些不同思路可以解决该问题？ | 多个候选方向及其价值与代价比较 | 不收敛为最终范围，不编写 Spec |
| 1.6 | 形成产品假设 | 我们目前相信什么，最应先验证什么？ | 目标用户、价值主张、差异化假设与关键风险 | 不是已成立的结论，也不是 Roadmap |

### 理由与边界

- 1.1 与 1.2 收集不同证据：用户/问题证据与外部解决方案证据。将两者分开，可以避免把竞品功能当作
  用户需求。
- 当现有证据不足时，1.1 包含与决策相称的用户研究，例如访谈、观察或分析现有数据。研究深度与
  决策相称；发现需区分观察事实、用户陈述、解释和假设。用户研究是发现阶段的一项活动，不是
  独立阶段或强制关卡。
- 1.3 在判断机会之前先框定问题。它是本文提出的细化；当前 `flow.zh-CN.md` 将这一框定视为发现和
  机会判断工作的一部分，而不是一个单独命名的步骤。
- 1.4 使用 1.1–1.3 判断机会。它不选择功能，也不承诺范围。
- 1.5 发散多个方向；1.6 将选定的方向转成一个可验证的假设。设计与执行验证实验属于第 3 阶段，
  不属于本阶段。
- 研究深度与决策相称。一个范围较小的功能可能只需要快速扫描，或明确决定无需更深入的研究。
- 本阶段不创建正式 Spec。发现笔记与证据在有帮助时可以放在当前工作目录中。

### 参考来源

本文的拆分对照了以下公开实践。它们为边界选择提供参考，但不是 CoolFlow 的规范：

- Teresa Torres，[Product Discovery Basics](https://www.producttalk.org/2021/11/product-discovery/)：
  成果 → 机会 → 解决方案；将机会空间与解决方案空间分开。
- Design Council，[The Double Diamond](https://www.designcouncil.org.uk/our-resources/the-double-diamond/)：
  在开发与交付方案之前，先发现并定义问题。
- Nielsen Norman Group，[Design Thinking 101](https://www.nngroup.com/articles/design-thinking/)：
  共情、定义、构思、原型和测试是不同的活动。
- Marty Cagan，[The Four Big Risks](https://svpg.com/four-big-risks/)：价值、可用性、可行性和
  商业可行性作为评估维度。
- Strategyn，[Jobs-to-be-Done](https://strategyn.com/jobs-to-be-done/)：从尚未满足的成果出发，
  而不是从产品功能出发。
- Strategyzer，[Value Proposition Canvas](https://www.strategyzer.com/library/the-value-proposition-canvas)：
  分别描述客户问题与拟提供的价值，再验证两者的匹配。

## 2. Lightweight Strategic DDD

状态：`已确认`（2026-11-05）

**范围：** 初始战略领域发现。本阶段产生一个暂定的领域模型。战术领域设计——聚合、实体、值对象、
仓储、领域事件和事务边界——推迟到 Design Spec Loop（第 6 步）。

| ID | 活动 | 回答的问题 | 核心产出 | 边界 |
| --- | --- | --- | --- | --- |
| 2.1 | 界定领域范围与参与者 | 这个产品涉及哪一部分业务、哪些角色和工作对象？ | 领域范围、参与者/角色、核心工作对象、核心与辅助部分 | 不重新定义第 1 阶段的产品问题或目标用户；不设计技术模块 |
| 2.2 | 建立统一语言与核心概念 | 每个核心术语在这个领域里是什么意思？ | 术语表、定义、同义词与歧义、核心概念及关系 | 不收录所有 UI 标签或代码命名；跨上下文冲突留给 2.3 |
| 2.3 | 划分限界上下文 | 哪些概念共享一致含义？同一个术语在哪里含义不同？ | 上下文列表、每个上下文的语言与职责、上下文之间的关系 | 不是微服务、代码模块或部署边界；不决定接口 |
| 2.4 | 定义核心业务规则与不变量 | 哪些条件必须始终成立，状态如何变化？ | 不变量、业务规则、状态转换、例外与失败条件 | 不规定实现算法或数据库约束；不替代验收条件 |
| 2.5 | 用业务场景检验并确认模型 | 模型能否解释真实流程和边界情况，哪些仍未解决？ | 关键场景走查、修正后的模型、已确认理解、开放问题 | 不是用户验收或原型测试；不验证产品假设；不编写 Spec |

### 理由与边界

- 2.1 与 2.2 分开：2.1 确定观察范围；2.2 定义术语含义。合并这两项容易把产品名称、UI 标签和
  技术标识混入领域语言。
- 2.3 识别的是**语义**边界。限界上下文之后可能影响模块或服务边界，但在这里不决定部署或接口。
- 2.4 记录业务规则与不变量，而不是实现约束。数据库约束和代码级强制属于后续设计与实现。
- 2.5 使用业务叙述和纸上走查，暴露缺失的概念与规则。它不是原型、用户测试或验收决定。
- `docs/domain.md` 中记录的模型是暂定且持续演进的。战术设计和代码级模型细化发生在第 6、7 步；
  新的领域理解可以通过 Evolution Loop 回到本阶段。
- 本阶段与项目复杂度相称。小型或熟悉的领域可能只需要核心术语、关键规则和一个上下文。不要为了
  执行 DDD 而虚构多个上下文。EventStorming、Domain Storytelling 和上下文映射都是可选方法。

### 参考来源

本文的拆分对照了以下公开实践。它们为边界选择提供参考，但不是 CoolFlow 的规范：

- Eric Evans，[Whirlpool Process of Model Exploration](https://www.domainlanguage.com/ddd/whirlpool/)：
  模型探索不是开发流程，应嵌入迭代式设计。
- Martin Fowler，[Ubiquitous Language](https://martinfowler.com/bliki/UbiquitousLanguage.html)：
  共享的严格语言随领域理解不断演进。
- Martin Fowler，[Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)：
  大模型被划分为语义上下文；上下文不是代码模块。
- DDD Crew，[DDD Starter Modelling Process](https://github.com/ddd-crew/ddd-starter-modelling-process)：
  领域发现、分解、战略和战术设计是迭代过程，不是线性序列。
- Domain Storytelling，[DDD with Domain Storytelling](https://domainstorytelling.org/domain-driven-design)：
  故事支持战略设计、统一语言以及后续的战术设计。
- EventStorming，[EventStorming](https://www.eventstorming.com/)：协作式领域探索可以发现事件、
  边界和开放问题。

## 3. Concept Prototype → Validation

状态：`已确认`（2026-11-06）

**范围：** 在承诺 MVP 范围之前，对最危险的假设进行限时验证。原型是可能的验证载体之一，
不是必需项。当薄 MVP 是观察行为最便宜、最可靠的方式时，可以把它用作实验；它不替代 Roadmap
决策，也不会自动成为生产代码。

| ID | 活动 | 回答的问题 | 核心产出 | 边界 |
| --- | --- | --- | --- | --- |
| 3.1 | 识别并排序关键假设 | 哪些信念最可能推翻方向，哪些应先验证？ | 按重要性和现有证据强弱排序的 1–2 个关键假设 | 不枚举所有假设；不测试低风险项 |
| 3.2 | 设计最小验证与时间盒 | 哪种方法、哪些参与者、什么结果和期限足以做决定？ | 验证计划：方法、参与者/样本、任务或实验步骤、成功标准和时限 | 不在定义问题前制作原型；不进行开放式研究 |
| 3.3 | 制作最小验证载体 | 能产生相关证据的最便宜载体是什么？ | 可点击 HTML、Figma 或纸面原型、逻辑原型、技术 spike、问卷、落地页或数据分析材料 | 不追求生产质量或构建完整产品；spike 代码不进入生产 |
| 3.4 | 执行验证并收集证据 | 实际发生了什么，证据有多强？ | 目标用户行为、技术结果、数据、失败案例和证据强度 | 不用内部意见替代用户证据；不把可运行的 spike 当作已完成功能 |
| 3.5 | 解释结果并决定下一步 | 继续进入 MVP、调整、回到前面，还是停止？ | 决策、已知风险、开放问题和下一步 | 不把单次测试当作普遍证明；不无限期延长验证 |

### 理由与边界

- 3.1 合并识别与排序，避免额外的流程仪式。选择一到两个既重要、又缺乏证据的假设；不要试图
  验证所有内容。
- 3.2 根据风险选择方法。用户理解和交互风险适合概念原型或可点击原型；可行性风险适合技术
  spike；需求风险可能需要落地页、waitlist 或真实行为数据。
- 3.3 使用最便宜且足够的验证载体。AI 生成的可点击 HTML 是概念和基础交互验证的常见轻量选项，
  但不能证明技术可行性或商业可行性。技术 spike 代码是可丢弃的。
- 3.4 收集直接证据，而不是意见。面向用户的假设应尽量用目标用户验证；技术假设应在有代表性的
  环境中验证。记录哪些部分是模拟的，哪些是真实的。
- 3.5 标注证据强度并做出明确决策。如果测试设计本身有缺陷，应先修正测试，再判断产品是否失败。
  如果证据推翻了产品方向或范围，使用 Evolution Loop。
- 当薄 MVP 比原型更便宜或更可靠时，可以把它用作实验。它仍然是实验：不替代 Roadmap 决策，
  也不会自动成为生产代码。
- 当风险低或现有证据充分时，跳过本阶段并记录原因。当证据足以选择 MVP 范围时退出，而不是等到
  所有假设都确定。剩余不确定性必须记录为已知风险。

### 参考来源

本文的拆分对照了以下公开实践。它们为边界选择提供参考，但不是 CoolFlow 的规范：

- Teresa Torres，[Assumption Testing](https://www.producttalk.org/assumption-testing/)：
  按重要性和证据排序假设，一次测试一个假设，先定义成功标准并跟踪证据。
- Strategyzer，[Testing Business Ideas](https://www.strategyzer.com/library/testing-business-ideas-book)：
  使用假设映射，并按成本、时间和证据强度选择实验。
- GV，[The Design Sprint](https://www.gv.com/sprint/)：在时间盒内用真实感原型和真实用户回答
  关键问题。
- Eric Ries，[The Lean Startup principles](https://theleanstartup.com/principles)：把 MVP 当作
  实验，使用验证性学习，而不是用产出数量衡量进展。
- Nielsen Norman Group，[Paper Prototyping](https://www.nngroup.com/articles/paper-prototyping/)：
  低成本原型可以在写代码前发现重要的可用性问题。

## 4. Roadmap

状态：`已确认`（2026-11-06）

**范围：** 产品级 Roadmap。它定义产品方向、当前版本和后续方向，不是功能级发布计划或任务清单。
功能行为和验收条件属于 PRD 或 Spec；实现任务属于 Agent 会话，仅在必要时写入 `tasks.md`。

| ID | 活动 | 回答的问题 | 核心产出 | 边界 |
| --- | --- | --- | --- | --- |
| 4.1 | 明确产品方向与当前版本目标 | 产品往哪走？当前版本要达成什么用户或业务结果？ | 产品方向、当前版本目标、成功指标 | 不写功能清单；不替代 `product.md` 中的产品简报 |
| 4.2 | 确定当前版本范围 | 哪些产品能力组成最小但完整、有价值、可验证的版本？ | MVP/当前版本范围、优先级理由、非目标、依赖与风险 | 不写详细验收条件；不拆实现任务 |
| 4.3 | 规划后续版本方向 | 之后可能做什么？置信度如何？ | 后续版本主题或方向、置信度、关键假设 | 不承诺未来功能或日期 |

### 理由与边界

- Roadmap 是产品级的。一个 Roadmap 版本可以包含多个工作目标；单个功能通常属于 PRD 或 Spec，
  而不是 Roadmap。
- 4.1 在确定范围前定义成果和成功指标。Roadmap 不是先列功能、再找理由的清单。
- 4.2 选择最小但**完整、有价值、可验证**的产品增量，而不是功能数量最少的版本。它记录明确的
  非目标、依赖、风险，以及安全、运营或数据迁移等必要支撑工作。
- 4.3 使用置信度，而不是虚假的精确度。只有真实的外部约束才使用日期。Now–Next–Later 是
  可选的置信度视图，不是强制格式。
- 记录 `roadmap.md` 是 4.1–4.3 的共同产出，不是单独活动。人类确认当前版本范围是退出条件，
  不是第四个步骤。
- 产品较小或范围已经明确时，使用简短的 Roadmap 记录或单个版本即可。不要为了填满模板而虚构
  后续版本。
- 当产品方向、版本范围或优先级变化时更新 Roadmap。常规功能级变更写入相关 Spec，不需要重写
  Roadmap。
- 计划中的内容不是已实现的证明。`features/` 仍然是已验收、已实现行为的权威位置。

### 参考来源

本文的拆分对照了以下公开实践。它们为边界选择提供参考，但不是 CoolFlow 的规范：

- ProdPad，[Now–Next–Later Roadmap](https://www.prodpad.com/blog/now-next-later-roadmap/)：
  按置信度而不是日期组织，避免把未来条目当成承诺。
- Teresa Torres，[Product Roadmaps](https://www.producttalk.org/product-roadmaps/)：
  Roadmap 应反映当前认知，Now 放方案、Next 放机会、Later 放成果。
- ProductPlan，[The Ultimate Guide to Product Roadmaps](https://www.productplan.com/learn/what-is-a-product-roadmap/)：
  Roadmap 传达产品方向与策略，不是完成品；应包含必要的技术与运营工作。
- Impact Mapping，[Impact Mapping](https://www.impactmapping.org/)：连接目标、参与者、影响和
  交付物，让范围始终与成果相关。

## 5. UI Prototype

状态：`已确认`（2026-11-06）

**范围：** 设计当前产品版本的关键流程、视觉方向、关键界面与状态，以及可点击原型。本阶段不是
完整设计系统、生产 UI 或 Spec。视觉方向是独立活动，不是画界面时隐含的一部分。

| ID | 活动 | 回答的问题 | 核心产出 | 边界 |
| --- | --- | --- | --- | --- |
| 5.1 | 明确设计目标与约束 | 这个版本必须支持哪些用户任务？平台、品牌、技术和无障碍约束是什么？ | 设计目标、关键任务、平台与约束、设计原则 | 不重新定义 Roadmap 范围；不设计技术架构 |
| 5.2 | 设计用户流程与信息架构 | 用户如何完成关键任务？页面和导航如何组织？ | 用户流程、信息架构、关键页面清单 | 不先做视觉细节；不写实现代码 |
| 5.3 | 探索视觉方向 | 产品应该看起来和感觉起来怎样？哪个方向最适合用户和品牌？ | 2–3 个使用风格板、mood board 或代表性界面的视觉方向；选定方向及理由 | 不是完整设计系统；不是每个最终页面 |
| 5.4 | 制作界面与可交互原型 | 选定方向如何应用到关键界面、状态和交互？ | 关键界面、空/加载/错误/成功状态、可点击原型和说明 | 不是生产代码；不接真实后端；不替代 Spec |
| 5.5 | 评审与可用性验证 | 用户能否理解并完成关键任务？视觉方向是否支持目标？ | 设计评审记录、任务测试发现、修改后的原型、开放问题 | 不是最终验收；不把内部意见当用户证据 |

### 理由与边界

- 5.1 使用 Roadmap 的当前版本范围，记录目标用户、关键任务、平台、现有品牌或设计系统、无障碍
  需求和重要技术约束。
- 5.2 先设计流程和结构，再进入视觉细节。静态线框图不足时，可以用 wireflow 或等价产物表达
  任务、导航、页面变化和系统反馈。
- 5.3 明确视觉方向。当选择会实质影响产品时，探索 2–3 个方向；使用风格板、mood board 或
  代表性界面比较色彩、字体、间距、图标、插画和动效。已有品牌或设计系统时优先复用。原型阶段
  通常不值得投入完整设计系统。
- 5.4 将选定方向应用到关键界面和状态，再连接成可点击原型。模拟的数据和交互必须明确标注。
- 5.5 结合设计评审和任务式可用性测试。尽量使用目标用户；小样本定性测试可以发现主要问题，但
  不是统计证明。如果视觉方向本身就是关键风险，应测试理解和品牌感知，而不只是问用户是否喜欢。
- 常规小改动可以复用现有模式，跳过正式视觉探索，并记录原因。不要为了填满模板而创建完整设计
  系统或覆盖所有边界界面。
- 产出放在 `docs/work/<objective>/prototypes/`。复杂设计决策可以记录在可选的 `design.md`；
  不新增强制 UI 文档。

## 6. Design Spec Loop

状态：`已确认`（2026-11-06）

**范围：** 为选定的增量创建一份可实施、可验证、可评审的统一 Spec。Spec 承载需求、可观察的验收
条件、技术方案、可选的战术领域设计、实施策略和验证方式。本阶段不是 PRD、实现、任务清单或最终
验收。代码评审和验收属于后续阶段。

| ID | 活动 | 回答的问题 | 核心产出 | 边界 |
| --- | --- | --- | --- | --- |
| 6.1 | 明确需求与验收条件 | 需要什么可观察的行为？哪些规则、例子和失败情况必须成立？ | 目标/非目标、用户行为、验收条件、关键例子和开放问题 | 不规定技术方案；不把实现细节混入验收条件 |
| 6.2 | 调查现有系统与约束 | 现有代码、数据、接口、架构和决策如何约束方案？ | 相关代码/数据、接口、约束、可复用模式和风险 | 不重写整个系统；不是对新增代码的评审 |
| 6.3 | 设计解决方案并起草统一 Spec | 准备如何实现？有哪些备选方案和取舍？如何验证？ | 统一 `spec.md`：技术设计、可选战术领域设计、实施策略、验证计划、取舍和假设；可选 `design.md` | 不写实现代码；不强制任务清单；不重复 PRD |
| 6.4 | 评审并修订设计 | 方案是否完整、可行、可测试，是否过度设计？ | 评审记录、修订后的 Spec、已解决或明确保留的阻塞项 | 不是代码评审；不是最终验收 |

### 理由与边界

- 6.1 用规则、具体例子和问题澄清行为。验收条件应可观察、可测试。开放问题应明确保留，而不是
  悄悄转成假设。
- 6.2 阅读现有系统以判断设计可行性。这与评审当前任务新产生的代码不同；代码评审属于
  Implementation Loop。
- 6.3 设计解决方案并起草统一 Spec。记录有意义的备选方案、取舍、失败情况、实施策略和验证方式。
  当技术细节过大时，可以选择单独的 `design.md`。
- 战术领域设计是 6.3 内部的可选检查点，不是独立活动。当领域有复杂不变量、状态转换、跨对象
  一致性或多个限界上下文时使用。记录聚合、实体与值对象、不变量落点、领域事件、仓储/领域服务
  职责和事务边界。只有持久领域理解变化时才更新 `docs/domain.md`；重要架构决策记录为 ADR。
- `tasks.md` 是可选的。编码 Agent 通常在会话中管理任务；只有当工作需要跨会话、跨 Agent 或
  跨时间保留时，才创建持久任务文件。
- 6.4 在重要实现前评审设计。新颖、复杂、高风险或不可逆的工作使用独立评审者；小改动使用轻量
  检查清单。解决重要阻塞项；产品关键取舍仍由人类决定。
- 维护一份权威 Spec。可选的 PRD、design 和 tasks 文档必须被链接，而不是重复。小修复可以使用
  简明的 Spec 或检查清单，而不是填满模板的每一节。

### 参考来源

本文的拆分对照了以下公开实践。它们为边界选择提供参考，但不是 CoolFlow 的规范：

- GitHub，[Spec Kit](https://github.com/github/spec-kit)：Spec 驱动开发将规格与计划、任务和
  实现连接起来，同时保留评审点。
- OpenSpec，[OpenSpec](https://github.com/Fission-AI/OpenSpec)：每个变更可以包含 proposal、

- Cucumber，[Introducing Example Mapping](https://cucumber.io/blog/bdd/example-mapping-introduction/)：
  用规则、例子和问题在开发前澄清验收条件。
- ADR GitHub organization，[Architectural Decision Records](https://adr.github.io/)：
  记录重要决策的背景、理由、取舍和后果。
